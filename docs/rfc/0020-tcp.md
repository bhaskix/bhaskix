## Summary

A TCP implementation in **`bin/tcpd`**, its own domain, holding no device and no DMA window. Its
core is a **pure transition function** in `bhaskix-net` — `(state, event) → (state, actions)` — with
no I/O, no clock and no allocation, so retransmission, reordering, loss and close can all be tested
on the host against a virtual clock. The domain around it is what turns actions into segments.

A connection's **byte stream lives in pages the program supplies**, one for each direction. The
receive window is therefore the free space in the program's own ring, and a connection costs the
memory of whoever asked for it rather than the service's. That is what lets a fixed-size service
survive a remote party that opens connections and never reads them.

**Minimal but correct**, and each absence is stated rather than implied: handshake, full state
machine including simultaneous open and close, measured retransmission timeout, delayed
acknowledgement, zero-window probing, orderly close with `TIME_WAIT`. **No congestion control, no
window scaling, no SACK, no timestamps, no path MTU discovery, no keepalive, no urgent data.**

## Motivation

**The roadmap's networking bullet names TCP and Phase 2 does not have it.** RFC 0018 delivered a
driver, a protocol service, UDP sockets and a DHCP client, and said in its own summary that TCP was
deliberately not there because it is "a state machine with its own failure modes, its own testing
plan and its own retransmission arguments". This is that document.

**Everything above the network wants a stream, not a datagram.** A shell that fetches a file, a
package tool, a remote console, the `bhaskixd-ai` advisory channel Phase 4 describes — none of them
can be written against UDP without inventing retransmission, ordering and flow control per program,
badly, four times. TCP is the one place in the system where writing it once is obviously right.

**And the prerequisite is finally real.** RFC 0018 could not have contained this: TCP needs four
timers before any argument about congestion control, and until 2026-08-13 nothing in this system
could wait for a length of time at all. RFC 0019 built the deadline, measured it, found it did not
work — the wake instant did not depend on the deadline — and fixed it the same day. A deadline is
now honoured to about a fifth of a millisecond. **A retransmission timeout derived from a clock that
could only be observed to a third of a second would have been noise**, so this RFC could not have
been written a day earlier than it was.

**What happens if we do nothing**: Phase 2 stays open on its last bullet, and every program that
needs a stream grows its own half-correct one.

## Design

### Where it runs, and the crossing it costs

```
   the wire
      │
  ┌───▼──────────┐  holds the device, the DMA window, the interrupt.
  │   bin/netd   │  Parses nothing.
  └───┬──────────┘
      │ frames, both ways, through a shared ring
  ┌───▼──────────┐  Ethernet, ARP, IPv4, ICMP, UDP. Owns the address.
  │   bin/ipd    │  Demultiplexes on the IP protocol field.
  └───┬──────────┘
      │ IPv4 payloads where protocol = 6, and segments to send back
  ┌───▼──────────┐  TCP, and nothing else. No device, no window, no
  │   bin/tcpd   │  address of its own — it is told what interface it is on.
  └───┬──────────┘
      │  connection capabilities, handed back in replies
  a program        holds one connection. Reaches that flow and nothing else.
```

**A third domain, and the reason is the one that split `netd` from `ipd`.** TCP is the largest
parser of remote input this system will contain, and it is the one with *state* a remote party can
drive — a datagram parser forgets each packet, a TCP endpoint remembers sequence numbers, windows
and timers for as long as the peer keeps it alive. Putting that in `ipd` would mean a bug in the
most complex remote-driven code in the system takes down every working UDP socket, including the one
that holds the machine's DHCP lease.

**And it is not free.** RFC 0018 step 7 measured the `netd`↔`ipd` boundary at **34–149 µs a round
trip** with the two domains on separate processors, against **10–16 µs** with them folded into one.
A third domain adds a second crossing in each direction. That is the honest cost of this split and
it is stated here rather than discovered at step 7 again: **a TCP round trip through this stack will
cost more than a UDP one by roughly one crossing each way**, and the measurement is in the
implementation plan rather than promised in a summary.

**Why `ipd` demultiplexes rather than `netd`.** `netd`'s defining property is that it parses
nothing — it holds the device and understands no protocol, which is what makes its DMA authority
safe to hold. Asking it to route by IP protocol number would require it to parse an IPv4 header,
which is the one thing it is defined not to do. `ipd` already parses that header, already does
reassembly, and already has to decide what a datagram is for. TCP is one more arm of a decision it
makes anyway.

### The state machine is a pure function, and this is the most important decision here

```rust
pub fn step(state: Tcb, event: Event, now: Instant) -> (Tcb, Actions)
```

No I/O. No clock — the time is an argument. No allocation. No knowledge that domains, rings or
capabilities exist. `Event` is an arriving segment, a call from the program, or an expired timer;
`Actions` is a bounded list of "send this segment", "arm this timer", "wake the program", "the
connection is now dead".

**Everything that is hard about TCP is then testable on the host**, with a simulated peer and a
virtual clock: a lost segment, a reordered pair, a duplicate `SYN`, a `RST` in each of eleven
states, a retransmission that backs off, a `FIN` crossing a `FIN`, a peer that advertises a zero
window and never opens it. None of that needs QEMU, a device, or a network, and `docs/coding-style.md`
calls a subsystem that can only be tested in QEMU a design smell. **TCP is the subsystem where that
rule pays for itself or is worthless**: its interesting behaviour is precisely the behaviour a live
network will not reproduce on demand.

It also means the fuzz target is the state machine itself and not merely its parser — arbitrary
sequences of arbitrary segments driven into arbitrary states, asserting only that it does not panic
and that its invariants hold.

**Where the impurity goes**: `bin/tcpd` is the loop that reads the ring, calls `step`, and performs
the actions. It is expected to be the smaller half.

### A connection's stream lives in the program's pages

Two `Memory` objects per connection, supplied by the program at `CONNECT` or `LISTEN` time and
mapped by `tcpd`: one ring the program writes and `tcpd` sends from, one `tcpd` writes and the
program reads.

This is not a memory-management convenience, it is the flow-control design:

- **The receive window is the free space in the program's ring.** A program that stops reading
  advertises a shrinking window and eventually zero, which is exactly what TCP flow control is for
  and requires no separate accounting.
- **A connection costs the memory of whoever opened it.** `bin/ipd` today holds a 384-byte buffer
  per socket in its own domain across four sockets (`user/ipd/src/main.rs:594`), which is fine for a
  datagram and impossible for a stream: sixteen connections with 64 KiB windows is a megabyte of
  service memory a remote party decides how to fill. Here the service holds control blocks, and the
  bytes are the program's problem.
- **Retransmission needs no second copy.** Unacknowledged bytes stay in the program's send ring
  until they are acknowledged; the ring's tail advances on `ACK`, not on transmission. A program
  that corrupts its own unsent data corrupts its own stream and nobody else's.

The `Actions` a `step` returns therefore name *ranges of the stream*, not buffers — `send bytes
[una+off, una+off+len)` — and `bin/tcpd` reads them out of the program's ring when it builds the
segment. The state machine never touches the bytes, which is the second reason it stays pure.

**Out-of-order segments are dropped, not buffered**, and this is the one place where "minimal"
costs performance rather than features. A segment arriving beyond the next expected sequence number
is discarded and not acknowledged, so the peer retransmits. This is permitted, it is correct, and it
turns a single loss into a stall of one retransmission timeout. A reassembly queue is the obvious
first thing to add and it is an open question below rather than a silent omission.

### The socket shape does not change, which was RFC 0018's whole obligation

RFC 0018 committed to a socket that could carry TCP "so it does not have to reopen anything here",
and this section is the check on that promise. A connection is a **badged capability to `tcpd`'s own
endpoint**, minted with `HAND`, landing in the slot the caller named with `EXPECT`, badged
`(index, generation)` so a capability held across a close names a connection that no longer exists.
Identical to a UDP socket and to a directory handle. **No new object kind, and no kernel change at
all** — which is the third time that sentence has been true and is now evidence rather than hope.

The one constraint RFC 0018 recorded in advance was that an *accepted* connection is a socket the
service mints at a moment the program did not initiate, and that this only works if the program is
waiting in a call. So `ACCEPT` is a call the program blocks in, and the constraint is met by the
design it was written for.

Methods, at 58 and up. `DISARM` is 57 and is the highest allocated; there is no gap this time.

| Method | Meaning |
|---|---|
| `CONNECT` 58 | destination address and port, the two ring capabilities, the slot to put the connection in. Blocks until the handshake completes or fails. |
| `LISTEN` 59 | local port; returns a *listener* capability, badged separately from a connection |
| `ACCEPT` 60 | on a listener: blocks until a connection is established, and the reply carries it |
| `SEND` 61 | on a connection: "I have written `n` bytes into the send ring". No payload in the message. |
| `RECV` 62 | on a connection: "I have consumed `n` bytes"; the reply says how many are available. Blocks if none, unless asked not to. |
| `SHUTDOWN` 63 | half-close: no more data this way. The other direction keeps working, which is what makes a request/response protocol expressible. |
| `CLOSE` 54 | reused, unchanged in meaning: end the binding and revoke the rings |

**A listener is a different capability from a connection** and not merely a differently-badged one,
because the operations do not overlap: you cannot `SEND` on a listener and you cannot `ACCEPT` on a
connection. The badge carries which it is, and a method applied to the wrong one is refused rather
than reinterpreted.

### Timers, and the shape RFC 0019 asked for

Four, per connection: **retransmission**, **delayed acknowledgement**, **zero-window probe**, and
**`TIME_WAIT`**. RFC 0019 gives one deadline per notification and says explicitly that a service
needing many keeps its own ordered list and arms the **nearest**. That is what `tcpd` does, and it
is the workload `M4-10b`'s timer wheel has been waiting for since M4 — an ordered list in a service,
which is what a wheel does internally, built where it can be measured before it is generalised into
the kernel.

The serve loop is then the one RFC 0010 spent two questions arguing towards, and it already exists
in `bin/ipd`: one blocking `Recv` that returns a **caller**, a **frame** or a **timer**, told apart
by badge bits. `ipd`'s loop handles two of those three today (`user/ipd/src/main.rs:739`); `tcpd`'s
handles three, and needs nothing new to do it.

### Retransmission timeout, measured rather than chosen

Jacobson/Karels smoothed round-trip time and variance, with **Karn's algorithm** — a retransmitted
segment's acknowledgement does not update the estimate, because it cannot be attributed to a
particular transmission. Exponential backoff on repeated loss, a floor and a ceiling, and a
connection abandoned after a bounded number of attempts.

The floor deserves a number rather than a tradition. The usual 200 ms floor exists because
historical clocks were coarse; **this system's deadline was measured on 2026-08-14 as late by a
median of 0.065–0.226 ms and a worst sample of 0.819 ms across three runs**, so a floor in the low
milliseconds is expressible here. It is left as an open question rather than picked now, because a
number chosen without a caller is the mistake RFC 0019's own question 1 records.

### The initial sequence number, and the entropy this system does not have

**A TCP initial sequence number must be unpredictable**, or an off-path attacker who can guess it
can inject data into a connection without ever seeing a packet from it. This is not a hardening
nicety; it is the difference between TCP being safe on a network and not.

**And this system has no source of randomness.** Not a weak one — none. There is no `rdrand`, no
`rdseed`, no entropy pool, and no kernel interface that returns an unpredictable number anywhere in
the tree; the only `Rng` is a seeded mutation harness in `kernel/src/elf.rs` used by a test. Even
KASLR is not ours: the kernel *observes* a slide the bootloader chose
(`kernel/src/lib.rs:10599`).

So this RFC has a prerequisite it cannot pretend away, and it is step 1 of the implementation plan:

- **`RDRAND` behind a `CPUID` check**, in `arch`, as the source. Available on every processor this
  project can realistically target and on QEMU's `-cpu max`, which is what the harness boots.
- **A refusal, not a fallback, when it is absent.** A machine with no `RDRAND` gets no TCP and is
  told why. The tempting fallback — seed from the TSC — produces a number an attacker who can
  estimate uptime can narrow enormously, and shipping that *unlabelled* is worse than shipping
  nothing, because the next reader assumes the problem was solved.
- **ISN by RFC 6528's construction**: a monotonic clock component plus a keyed function of the
  four-tuple, so that sequence numbers do not repeat across connections on the same pair of ports
  and are not guessable from another connection's.

**It became [RFC 0021](0021-unpredictability.md)**, decided 2026-08-14, and that document is
smaller than this paragraph expected for a reason worth carrying back here: `RDRAND` is
**unprivileged**, so there is no capability to design and no system call to add. The kernel's whole
part is a feature bit, a boot line and a policy — and the policy is that the *caller* refuses.
`bin/tcpd` is that caller: on a machine that cannot be unpredictable, it does not start.

### What is deliberately not here

| Not included | Why, and what it costs |
|---|---|
| **Congestion control** | Slow start, congestion avoidance, fast retransmit and recovery are their own document. Without them this stack is a bad citizen on a shared network and a correct one on a link it does not share. It sends a fixed window and backs off only on timeout. **It must not be exposed to the internet in this state**, and the code should say so where the window is set. |
| **Window scaling (RFC 1323)** | Caps the window at 64 KiB, which caps throughput on a long fat path. Irrelevant at the rates this stack reaches through an emulated NIC and three domains. |
| **SACK** | Makes a single loss cost one retransmission instead of a stall. Wanted, and it is the natural companion to the reassembly queue this RFC also leaves out. |
| **Timestamps** | Improves the RTT estimate and gives PAWS protection against wrapped sequence numbers. PAWS matters at speeds this system will not reach for years. |
| **Path MTU discovery** | The MSS is derived from the interface MTU (`net/src/eth.rs:31`, 1500) and never revised. On a path with a smaller MTU this stalls rather than degrades, which is the honest failure and is worth stating. |
| **Keepalive** | A connection to a peer that vanished stays until the program closes it. |
| **Urgent data** | Widely considered a mistake, inconsistently implemented, and used by almost nothing. The `URG` bit is parsed and ignored. |
| **Listening on a wildcard address** | One interface exists; a listener names the port and gets that interface. |

### Failure behaviour

| Situation | Behaviour |
|---|---|
| Connection table full | `CONNECT` and `ACCEPT` refuse with `CONGESTED`. A fixed table refusing is this project's posture everywhere; a growing one's failure is somebody else's out-of-memory. |
| `TIME_WAIT` fills the table | The real version of the row above, and the one that is remotely triggerable: a peer that opens and closes connections leaves slots reserved for 2×MSL. `TIME_WAIT` entries are held in a **separate, smaller table** than live connections, so exhausting them costs new connections their protection against old duplicates and never costs an established connection its slot. |
| Peer never answers `SYN` | Retransmit with backoff, then fail the `CONNECT` with a status that says "no answer", distinguishable from "refused". |
| `RST` arrives | The connection dies; the program's next `SEND` or `RECV` is told, with a status distinct from an orderly close. A `RST` is validated against the window before it is believed, or an off-path attacker resets connections for free. |
| Segment fails a check | Counted by reason and dropped. Every refusal path is a host test, as RFC 0018's six parsers are. |
| Program stops reading | The window closes, the peer stalls, and nothing in `tcpd` grows. This is the design working, not a failure. |
| Program dies holding a connection | Its rings are revoked with its address space; `tcpd` sees the revocation, sends a `RST`, and frees the control block. |
| `tcpd` dies | Every connection dies with it and every blocked caller is told `Revoked` — RFC 0017 step 3's abandonment, unchanged. |
| `tcpd` hangs | Every caller blocks for ever. **Unsolved, and this RFC makes it worse than RFC 0018 did**: see open question 4 there, and the note below. |
| `ipd` dies | `tcpd` loses its only path to the wire and fails every connection. |

**On the hang, specifically.** RFC 0018's open question 4 says a stack is the worst subsystem in
which to have no timeout on `Recv`, because it is the first one with a legitimate reason to be
slow. TCP is that reason made permanent: a program blocked in `ACCEPT` is *supposed* to wait
indefinitely. RFC 0019 has since supplied the mechanism a policy would use — a program can arm a
deadline and be woken by it — so the missing piece is now genuinely a decision rather than code.
**This RFC does not make that decision** and must not be accepted as though it had.

### Concurrency, and where `unsafe` is needed

`bhaskix-net` gains the state machine and stays `#![forbid(unsafe_code)]` with `unsafe_budget = 0`.
That is the property that makes it fuzzable as ordinary code, and TCP is the last thing that should
be allowed to erode it.

`bin/tcpd` needs `unsafe` exactly where `bin/ipd` does and nowhere else: volatile access to the
shared rings it has mapped. No device registers, no DMA, no interrupt. It runs one thread with one
blocking call, so there are no locks and nothing runs in interrupt context.

## Alternatives considered

| Alternative | Why rejected | Would reconsider if |
|---|---|---|
| **TCP inside `bin/ipd`** | One fewer crossing each way, and a measurable one — 34–149 µs a round trip. But it puts the system's largest remote-driven *stateful* parser in the domain that holds the machine's address and every UDP socket, including DHCP's. The split that separated `netd` from `ipd` was made on a weaker version of this argument. | If measurement shows the extra crossing dominates a realistic workload *and* the state machine can be isolated within one domain some other way. |
| **TCP in the nucleus** | Contradicts the project's one architectural claim, for the code with the worst threat profile in the system. | Never. |
| **A per-program stack library, `tcpd` hands out flows** | The most capability-native option — a compromised stack compromises one program. RFC 0018's table already records it as "the most interesting thing in this table", deferred because it needs flow demultiplexing below it. TCP makes it *more* attractive and no more available. | It deserves its own RFC, after this one works and can be compared against. |
| **The stream buffered in `tcpd`'s own memory** | Simpler, and how most stacks do it. But it makes the service's memory a resource a remote party spends: sixteen 64 KiB windows is a megabyte the peer decides how to fill, and the fixed table would have to be small enough to be useless or large enough to be a target. | If a use appeared where the program genuinely cannot supply pages — a program too small to hold a window — and even then a per-domain quota is the better answer. |
| **A queue of out-of-order segments in v1** | It is the difference between one loss costing a retransmission and one loss costing a stall. Left out because it is the first thing that wants memory the service must own, which is the design decision above, and because it can be added without changing an interface. | Immediately, if measurement on a lossy path shows the stall dominates — this is the most likely first amendment. |
| **Congestion control in this RFC** | Slow start and recovery are an argument of their own, and every part of the state machine below them can be built and tested first. Shipping them together would mean neither is reviewable. | It is the obvious next RFC, and this document is shaped so it does not have to reopen anything here. |
| **Vendoring an existing TCP (`smoltcp`)** | `ALLOWED_EXTERNAL` in `tools/check-deps.py` is empty by policy and `docs/security.md` §1 treats a dependency as attack surface. The one exception ever made is host-only and never boots. | If it could be vendored under this project's `unsafe` budget, fuzzed as our own code, and reviewed as such — which is most of the cost of writing one. RFC 0018 rejected the same option for the same reason. |
| **Seeding the ISN from the TSC because there is no RNG** | It makes the sequence number guessable to anyone who can estimate the machine's uptime, and it *looks* solved, which is worse than being visibly absent. | Never as a silent fallback. Acceptable only if labelled at runtime as insecure, and even then the refusal is cheaper. |
| **A `Stream` object kind in the kernel** | The kernel gains an object it cannot benefit from, and RFC 0018 already made and corrected this exact mistake with `ObjectKind::Socket`. | Never; the correction is recorded in RFC 0018 §"A socket is a capability". |

## Security implications

**New authority**: a connection capability, and a listener capability. Both are narrow by
construction — one flow, or one local port — and neither is ambient. A program with neither cannot
name the network, exactly as before.

**New reachable-without-a-capability surface: none**, with one sharpening. A *listener* accepts
connections from anyone who can reach the port, so the program holding it is exposed to unsolicited
remote input in a way a `CONNECT`-only program is not. That is what a listener is for; it is worth
saying because it is the first capability in this system whose whole purpose is to accept strangers.

**New parsers for untrusted input**: the TCP header and its options, plus — and this is the material
change — **a state machine driven by untrusted input**. Every parser this project has fuzzed so far
forgets each input as it finishes with it. This one carries state between inputs that a remote party
chose, which means the fuzz target has to be the machine and not just the parser. Named in the
testing plan.

**New denial of service, and it is not the parser.** `TIME_WAIT` slot exhaustion, control blocks
held by half-open connections, and retransmission work driven by a peer that acknowledges nothing.
Answered by fixed tables, by a separate `TIME_WAIT` table, by a bounded retransmission count, and by
the design decision that the *stream* memory belongs to the program. Each has a test.

**A weakness this RFC creates and names**: without congestion control, this stack responds to loss
only by timeout. On a shared or congested path it will behave badly, and the honest statement is
that it should not face the internet until that RFC lands.

**The ISN is the security-critical number here**, and the entropy prerequisite above is the whole
of the answer. A predictable ISN makes off-path injection possible for an attacker who never sees a
packet.

## Performance implications

**Slower than UDP by roughly one domain crossing each way**, and the number to beat is measured:
34–149 µs a round trip across the existing two domains, 10–16 µs folded. What to measure, as a
distribution and not a mean:

- **Handshake to first byte**, and a round trip on an established connection, against the UDP
  numbers above so the third domain is priced rather than argued about.
- **Throughput on a bulk transfer**, which is where the fixed window and the missing window scaling
  show up, and where the copies — program's ring to segment, segment to `ipd`'s ring, to `netd`'s —
  become visible.
- **Time to recover from a single lost segment**, which is where "no out-of-order buffering" is paid
  for, and which is the measurement that decides whether the reassembly queue is the first
  amendment.
- **Retransmission timeout accuracy** against the deadline resolution RFC 0019 now provides.

A performance claim without a benchmark is a hypothesis, and this document's own predecessor had its
headline claim disproved by its step 7. None of the above is predicted here.

## Testing plan

**Host — and this is where nearly all of it belongs.** The state machine is a pure function, so:

- Every transition of the eleven states, including simultaneous open and simultaneous close.
- Loss, duplication and reordering, driven by a simulated peer over a virtual clock: no QEMU, no
  device, no timing flakiness.
- Retransmission backoff, Karn's algorithm, and a connection abandoned after its bounded attempts.
- Zero-window advertisement, the probe, and the window reopening.
- `TIME_WAIT` expiry, and an old duplicate arriving during it.
- A `RST` in each state, including one outside the window that must be ignored.
- **Watched failing, deliberately**: the project's rule is that a test that passes proves nothing
  until it can fail. Break the sequence-number comparison to use `<` instead of a wrapping compare
  and the reordering tests must go red; break Karn and the backoff test must.

**Fuzz**: the header and options parser, and — the one that matters — **the state machine driven by
arbitrary segment sequences from arbitrary states**, asserting no panic and that its invariants hold
(`snd.una ≤ snd.nxt`, the receive window never exceeds the ring's free space, no state has an
outgoing transition it cannot take). Twenty-four hours, as `elf::parse` and `DMAR` have run.

**QEMU**: a peer is needed, and QEMU's user-mode network can be one. `guestfwd` redirects a guest
TCP connection to a host-side command, so the guest connects to an address slirp answers and gets a
deterministic peer — **verified on this machine's QEMU 4.2.1**, which accepts
`guestfwd=tcp:10.0.2.100:9-cmd:...` on the `restrict=on` network the harness already boots. The gate
is then: connect, send a payload, receive it unchanged, close cleanly, and assert the connection
reached `TIME_WAIT` and left it. A second gate accepts an inbound connection the same way.

**Real hardware**: nothing here needs it beyond what M1-17 already owes.

   ephemeral ports as `49152 + index`, and `security.md` already claims a heap-base randomisation
   the system cannot perform. Step 1 below now consumes RFC 0021 rather than containing it.
2. **What is the retransmission floor?** The traditional 200 ms exists for clocks this system no
   longer has. Deferred until the measurement in step 6 says what the round-trip distribution
   actually looks like, rather than picked from tradition now.
3. **Is the out-of-order queue the first amendment, or is congestion control?** Both are deferred;
   which is more urgent is an empirical question the loss-recovery measurement answers.
4. **Who may listen on a privileged port?** There is no notion of privilege here and no `root` by
   design, so "ports below 1024 are special" has no mechanism to hang on. Probably the answer is
   that a listener capability is granted by whoever holds the interface, and the number is not
   special at all — but that is a claim about how services are launched, and Phase 2's supervisor is
   the thing that would have to express it.
5. **Does `tcpd` need its own address, or is it told?** It holds no interface and no DHCP lease. It
   is told, by the same configuration page `ipd` publishes today — but whether it should be able to
   *notice* the address changing, mid-connection, is not decided, and DHCP renewal will eventually
   make that concrete.

## Implementation plan

Each step leaves the tree green, as RFC 0018's and RFC 0019's did.

1. **The ISN**, on [RFC 0021](0021-unpredictability.md)'s `bhaskix-rand`: RFC 6528's construction,
   and `bin/tcpd` refusing to start on a machine that cannot be unpredictable. RFC 0021's single
   step lands first. **No longer blocked** — open question 1 is answered.
2. **The segment: header and options, parsed and built**, in `bhaskix-net`, with its fuzz target.
   Pure, host-tested, no state. The same shape step 1 of RFC 0018 took, and for the same reason.
3. **The state machine**, as `step`, with the simulated peer and the virtual clock. The bulk of the
   host tests land here, and nothing has crossed a domain boundary yet.
4. **`bin/tcpd`**: the domain, the loop over callers, segments and timers, the rings from `ipd`, and
   the connection and listener capabilities. The first step that boots.
5. **A connection to a real peer**, through `guestfwd`: connect, echo, close, `TIME_WAIT` observed.
   Then the same inbound, through `LISTEN` and `ACCEPT`.
6. **The measurement** — handshake, round trip, bulk throughput and single-loss recovery, as
   distributions, against RFC 0018 step 7's recorded numbers, in TRACKER.

Steps 1 to 3 are host-only and are most of the work. Step 4 is where it becomes a system. Step 6 is
what tells the next RFC — congestion control or reassembly — which one it should be.
